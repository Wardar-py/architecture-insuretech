# Анализ текущей архитектуры и риски роста

## Текущее состояние
- Сервис `ins-product-aggregator` синхронно опрашивает API всех страховых компаний, агрегирует данные и возвращает единый список в ответе на REST-запрос.
- `core-app` и `ins-comp-settlement` периодически вызывают `ins-product-aggregator` (раз в 15 минут и раз в сутки) и кэшируют результаты локально.
- `ins-comp-settlement` раз в сутки синхронно запрашивает `core-app` для получения списка оформленных за день страховок.
- Локальные кэши продуктов могут устаревать до 15 минут (core-app) или до суток (settlement), что приводит к риску продажи неактуальных тарифов.
- Отсутствует механизм надёжной доставки данных между сервисами.

## Риски при увеличении числа страховых компаний (до 10)
1. **Увеличение времени ответа `ins-product-aggregator`**  
   Синхронный опрос 10 внешних API увеличит задержку пропорционально числу компаний, особенно с учётом возможных сетевых проблем. Это нарушит SLA для вызывающих сервисов.

2. **Снижение отказоустойчивости**  
   Недоступность или медленный ответ одной из 10 компаний приведёт к таймауту всего запроса. Сервисы-потребители не получат данные вовсе, даже если 9 компаний ответили успешно.

3. **Эффект «снежного кома» при пиковых нагрузках**  
   Одновременные запросы от `core-app` и `ins-comp-settlement` к `ins-product-aggregator` (особенно ночной запрос settlement) могут перегрузить агрегатор и внешние API.

4. **Рассинхронизация данных**  
   Редкое обновление кэшей (сутки для settlement) при росте числа продуктов и частых изменениях тарифов приведёт к некорректным расчётам и ошибкам взаиморасчётов.

5. **Потеря данных при расчётах**  
   Синхронный REST-запрос от `ins-comp-settlement` к `core-app` для получения дневных страховок не имеет гарантий доставки. Если `core-app` временно недоступен, расчёт пропускается, что критично для бизнеса.

6. **Жёсткая связанность сервисов**  
   Прямые REST-зависимости делают систему хрупкой: изменение API одного сервиса или внешней компании требует координации релизов.

## Предлагаемые решения
- **Внедрить Event-Streaming (Apache Kafka)** для асинхронного обмена данными.
- **Перевести обновление продуктов на событийную модель**: `ins-product-aggregator` асинхронно опрашивает страховые компании и публикует события `ProductUpdated` в Kafka; `core-app` и `ins-comp-settlement` подписываются и обновляют свои локальные представления в реальном времени.
- **Заменить синхронное получение оформленных страховок событием**: `core-app` публикует событие `InsurancePurchased` (через Transactional Outbox) при оформлении; `ins-comp-settlement` потребляет его и накапливает данные за день.
- **Использовать паттерн Transactional Outbox** для гарантированной публикации событий в рамках той же транзакции, что и бизнес-операция.
- **Оставить синхронный REST только там, где необходим немедленный ответ** (например, оформление страховки с получением предложений по ОСАГО для конкретного автомобиля). При этом агрегатор может использовать асинхронные запросы с fallback-стратегией.

Эти изменения устранят временные задержки, повысят устойчивость к отказам внешних систем, обеспечат консистентность данных и готовность к масштабированию до 10 и более страховых компаний.
